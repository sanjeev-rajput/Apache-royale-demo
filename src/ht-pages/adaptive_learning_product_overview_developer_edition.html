Product differentiation · Why this is more than a chatbot

A coordinated learning capability, not a single AI feature

The proposition combines curriculum context, educator-defined guidance, learning resources, assessment workflows and a pathway for using evidence to inform what happens next. The value is in how these parts work together.

Curriculum-aware context

Class, subject and topic give explanations, resources and practice a shared learning context.

Educator-governed behaviour

Educational expectations can be expressed through configuration and reviewed SME guidance rather than scattered subject-specific code.

Multiple ways to learn

Explanations, catalogue activities, videos, AI practice and question-bank practice contribute to a topic-focused experience.

Evidence with provenance

Assessment responses and outcomes can be retained with their source, distinguishing observed evidence from later interpretation.

Learner agency

Recommendations can guide the learner without removing available choices or forcing a fixed sequence.

Model flexibility

A centrally managed AI provider/model choice allows the deployment strategy to evolve over time.

The differentiator is not simply that AI can answer a learner. It is the ability to connect learning context, educational guidance, practice evidence and the learner’s next choice.
Configurable intelligence · A deliberate product choice

Adaptive Intelligence can be enabled when the use case and budget justify it

Evidence-driven adaptive analysis should be optional—not a prerequisite for the core learning experience. This creates a practical adoption path for organisations with different infrastructure, AI budgets and maturity levels.

Adaptive Intelligence · Off

Lightweight learning mode

  • Keep the core learning experience available.
  • Continue using the configured AI capabilities already required by the selected workflow.
  • Do not run the additional post-assessment evidence-interpretation step.
  • Keep assessment scoring and recorded outcomes independent of AI interpretation.

Intended for constrained hardware, lower-cost deployments, early pilots or organisations introducing adaptive analysis later.

Adaptive Intelligence · On

Evidence-informed learning mode

  • Use completed assessment evidence to inform a more tailored teaching response.
  • Consider responses, outcomes, feedback and the limits of available evidence.
  • Use the selected SME-authored profile guidance to shape interpretation and suggested next steps; profile metadata status does not currently block loading.
  • Keep recommendations optional and preserve learner choice.

Intended where expected educational value justifies additional AI processing and operating cost.

Implemented as a bounded backend POC control

When enabled, the backend makes one post-assessment teaching request after a completed assessment. A submitted attempt cannot be submitted again, preventing the same active attempt from triggering duplicate processing. If the optional request fails, the completed assessment and its history remain available. This switch does not turn off existing AI features.

Status: backend POC code implemented and automated tests passed. Live model behaviour, Royale rendering of the response metadata/message, and hosted deployment configuration still require validation. This is not a production-certified product setting.

Educator & SME view · Educational governance

Educational intent stays with the people who understand learning

The platform should not hardcode pedagogy. Subject-matter experts and instructional designers define the educational expectations; the application provides reusable mechanisms to apply them.

What educators and SMEs can govern

Existing configuration foundation

Learning catalogues

CSV-based catalogues currently include English, Mathematics and EVS examples. Catalogue entries can reference an instruction profile through instructionProfileId.

Instruction profiles

JSON profiles include SME ownership and lifecycle metadata such as owner, status, version and review notes, alongside response, quality and assessment guidance.

Language and conversation settings

A separate language configuration holds intent rules, aliases, messages, language behaviour and AI feature settings.

Governance principle

Profile status (including draft) is descriptive metadata; the current loader uses referenced profiles regardless of status. SME authorship, review notes and version history remain useful governance information, but status is not a runtime loading gate.

Subject-agnostic by design

The engine should not need a new hardcoded branch for every subject. Subject differences should be described through curriculum data, learning objectives when available, evidence expectations and SME guidance.

Illustrative subjectPossible evidenceSME-defined interpretation
MathematicsWorked steps, selected answer, numerical result, explanation.Whether the learner applied a concept or procedure correctly.
ScienceExplanation, observation, classification, application.Whether the learner can explain or apply a scientific idea.
English / languagesReading response, grammar choice, written or spoken response.Whether the learner demonstrates the targeted language skill.
Social StudiesInterpretation, chronology, source-based response, reasoning.Whether the learner can interpret information and support a conclusion.

Examples are illustrative. The current POC does not claim to support every evidence type above. Additional response formats and evaluation methods would need to be implemented and validated.

How to avoid misleading learner conclusions

  • An incorrect response is evidence, not automatic proof of a misconception.
  • Insufficient evidence must be an acceptable outcome.
  • Mastery criteria and recommendation bands must be reviewed by the relevant SME.
  • Feedback should be appropriate to the specific learning objective and learner context.
  • The learner should be offered helpful choices rather than forced into a rigid path.
For subject experts, curriculum leads, assessment designers and instructional designers.

AI provider flexibility and cost-aware operation

A shared provider-selection layer is intended to keep learning workflows independent of a specific model vendor and allow the operating choice to reflect hardware, latency, quality and cost requirements.

Architectural direction

Central model selection

Local development and hosted deployment can use centrally selected providers/models. Individual learning modules should not independently discover, switch or hardcode providers.

Planned control

Optional adaptive analysis

The additional evidence-interpretation step is intended to be independently switchable, controlling when the extra model workload is incurred.

Resilience principle

Graceful degradation

If optional interpretation fails, existing assessment results and core learning choices should remain available.

Deployment choice

Local or hosted AI

Deployments can evaluate local models or hosted services against privacy, infrastructure, response-time, quality and cost requirements.

Why this matters commercially

A buyer should not have to commit permanently to one model, hardware profile or AI cost structure. The intended architecture centralises that decision and makes the additional adaptive-analysis workload optional. Provider compatibility, performance and economics must be validated in the target environment.

Engineering guardrails

  • Do not hardcode subject names, topic names or educational thresholds in central Adaptive orchestration.
  • Do not allow an LLM to authoritatively set marks, answer keys or learner records.
  • Keep non-LLM resource and Question Bank functionality available when an LLM is unavailable.
  • Keep Adaptive, Agentic and AI K12 workflows separated unless a deliberate shared-service decision is approved.
  • Validate configuration structure and fail safely with useful diagnostics.
  • Do not claim a source-level check is equivalent to a full browser, security or load test.

Adaptive Learning assessment lifecycle

02 · ASSESSChoose sourceAI Practice or Question Bank; each uses its own generator/repository and evaluator.
03 · NORMALISECommon resultnormalizeAdaptiveAssessmentResult() and attachAssessmentQuestionDetails().

Both Adaptive assessment sources converge after deterministic evaluation. ADAPTIVE_INTELLIGENCE_ENABLED now governs the optional post-assessment teaching request: OFF skips that request; ON makes one bounded request through the central provider. It does not control question generation, scoring, or the other learning experiences.

Assessment authority

The LLM may generate question content and teaching explanations. It must not decide the authoritative answer key, correctness, marks or stored assessment result. Preserve source provenance and distinguish unanswered questions from answered-but-incorrect questions when constructing evidence.

Engineering guardrails and change protocol

Keep Adaptive, Agentic, Agentic Assessment, Question Bank and AI K12 workflows isolated.
Keep LLM provider/model selection central and model-agnostic.
Keep scoring, answer keys and marks deterministic and server-authoritative.
Preserve assessment source, question-level evidence and unanswered-answer distinction.
Keep all learner choices available; recommendations do not force a pathway.
Treat profile status as metadata; referenced draft profiles must continue to load.
Validate config shape and profile content; log actionable errors without leaking secrets.
An optional AI failure must not erase a completed assessment or block core non-AI features.
Add tests for both enabled and disabled feature states and for each assessment source.
Run regression tests for untouched experiences after a shared-service change.
Do not equate static source inspection with runtime, browser, security or load validation.
Update this architecture reference when a material workflow, path or configuration contract changes.
